# Architecture

## Layers

The service is organised in three layers with a one-way dependency flow:

```
routers/  ->  services/  ->  storage.py  ->  data/*.json
(HTTP)        (domain)       (data access)   (synthetic seed)
```

- **routers/** — FastAPI routers, one per resource (`health`, `appointments`,
  `clients`, `therapists`). They handle HTTP concerns only: parsing input,
  calling into services or storage, shaping responses.
- **services/** — domain logic that does not belong in a router, such as
  computing therapist availability and detecting booking conflicts
  (`services/scheduling.py`).
- **storage.py** — a small in-memory store loaded from the JSON seed files at
  start-up. This is a placeholder for a real database.

## Request flow

A request to `GET /appointments?date=2026-03-04`:

1. `routers/appointments.py` receives the request and reads the `date` query.
2. It asks `storage.Store.list_appointments(...)` for the matching records.
3. The response is serialised back to JSON by FastAPI.

## Data

Seed data lives in `data/` and is generated by `scripts/generate_data.py`
(reproducible via a fixed random seed). It is entirely synthetic. The store
loads it into memory on start-up; there is no persistence between restarts.

## Known limitations / roadmap

- **No real database.** The in-memory store is a stand-in. A future version
  would move to PostgreSQL with a migration tool.
- **No authentication.** The API is unauthenticated for now.
- **Operational setup is immature.** Containerization, CI, configuration and
  secret handling, and observability are all early and need work.
- **No pagination.** List endpoints return full result sets.
